# SearchTrail для Obsidian

Версия MVP: **0.1.1**.

Локальный плагин для планирования поиска, ведения журнала и хранения карточек найденных материалов. Подходит для исследований и рабочих задач: статей, документации, отчётов и веб-страниц.

Основные сущности: **проект → запрос → версия запроса → выполнение поиска**. Проект объединяет исследовательский вопрос, критерии отбора и историю работы. Выполнение хранит снимок использованной версии, поэтому дальнейшее редактирование запроса не меняет прошлые результаты.

С версии 0.1.1 плагин называется **SearchTrail**; прежнее название — Research Search Ledger. Для совместимости сохраняются Obsidian plugin ID `research-search`, каталог установки, идентификаторы команд и формат данных v1. Переименование не требует переноса существующих поисковых проектов.

## Возможности MVP

- Проекты с исследовательским вопросом, критериями отбора и описанием работы с дубликатами.
- Запросы со статусами «Черновик», «Активный», «Приостановлен» и «Завершён».
- Версии определения запроса: база, платформа, выражение, поля поиска, фильтры, период публикации, языки и адрес поиска.
- Простой составитель выражения из трёх групп терминов: `OR` внутри группы и `AND` между группами. Получившийся текст можно отредактировать.
- Журнал выполнений со снимками запросов, датами, назначением, статусом, статистикой и примечаниями.
- Исправление записи о выполнении с обязательной причиной и сохранением предыдущего состояния.
- Экспорт в Markdown, CSV и JSON.
- Импорт проекта из JSON с сохранением идентификаторов, версий и истории.
- Вкладка «Материалы»: карточки с необязательными DOI, авторами, годом и ссылками, состояниями просмотра и отбора, историей и привязкой к нескольким поискам.
- Работа с проектами, запросами и выполнениями через MCP при включённом Local REST API with MCP.

Плагин сохраняет сведения, которые вводит исследователь. Поиск выполняется в выбранной базе или на сайте; число результатов и итоги обработки переносятся в журнал вручную.

Поля выбора проекта, фильтров и формата экспорта отмечены стрелкой вниз. У раскрывающихся подробностей стрелка направлена вправо в закрытом состоянии и вниз в открытом. Такие же индикаторы используются в формах.

## Установка готовой сборки

Для разработки открой корень репозитория в VS Code. После сборки установи плагин в отдельное тестовое хранилище командой `npm run install:dev -- --vault "/absolute/path/Test Vault"`.

Для ручной установки:

1. Открой отдельное тестовое хранилище Obsidian.
2. Создай каталог `<хранилище>/<configDir>/plugins/research-search/`.
3. Скопируй туда только корневые `main.js`, `manifest.json` и `styles.css`. Если `main.js` отсутствует, сначала выполни `npm ci` и `npm run build`.
4. При стандартных настройках три файла должны находиться непосредственно в `<хранилище>/.obsidian/plugins/research-search/`.
5. Перезапусти Obsidian и включи **SearchTrail** в настройках сторонних плагинов.
6. Открой панель плагина через палитру команд Obsidian.

Команда `npm run package` создаёт установочный архив `searchtrail-0.1.1.zip` с папками `plugin/research-search/` и `source/searchtrail/`. Имя npm-пакета — `searchtrail`; каталог плагина сохраняет технический ID `research-search`.

`configDir` означает каталог настроек конкретного хранилища. Если он переименован, используй его фактическое имя. Ручная установка файлов сборки соответствует подходу из [официального примера плагина Obsidian](https://github.com/obsidianmd/obsidian-sample-plugin#manually-installing-the-plugin).

## Первый проект

1. Создай проект, например «Прогнозирование состояния телекоммуникационного оборудования».
2. Запиши исследовательский вопрос и критерии отбора: какие объекты, методы и виды публикаций рассматриваются.
3. Добавь запрос и укажи базу, платформу, выражение и ограничения.
4. Выполни запрос на выбранной платформе. При необходимости используй сохранённый адрес поиска.
5. Добавь выполнение в журнал: дата, назначение, статус, известные числа и примечания.
6. При изменении выражения отредактируй определение запроса. Новая версия сохранится отдельно от предыдущей.
7. После следующего поиска добавь новое выполнение, чтобы сохранить результаты отдельно от прежнего запуска.

Для первого проекта можно начать с одного запроса и заполнить только известные сведения. Пустые числовые поля остаются неизвестными; заполнять их нулями не требуется.

## Что хранится в запросе

| Поле | Смысл |
| --- | --- |
| База / источник | Какой корпус публикаций или ресурс исследуется |
| Платформа / интерфейс | Через какой сервис или интерфейс выполнен поиск |
| Выражение | Полный текст запроса с операторами, скобками и кодами полей |
| Поля поиска | Например, заголовок, аннотация, ключевые слова |
| Фильтры | Применённые ограничения и пояснения к ним |
| Период публикации | Ограничение по датам публикации, если оно использовалось |
| Языки | Языковые ограничения либо явное указание, что их нет |
| Адрес поиска | Ссылка на поисковый интерфейс или сохранённый запрос |

База и платформа разделены: один корпус может быть доступен через разные интерфейсы, а один интерфейс — обслуживать несколько корпусов. Для веб-ресурса можно указать его название в поле источника, а в платформе — используемый интерфейс.

При изменении любого поля определения создаётся следующая версия. Переименование запроса или смена его рабочего статуса сами по себе не создают новую версию выражения. Комментарий к изменению помогает объяснить, зачем была подготовлена новая версия.

### Условный пример для телекоммуникационной тематики

```text
("telecommunications equipment" OR "network equipment")
AND ("failure prediction" OR "predictive maintenance")
AND ("optical transceiver" OR "power supply")
```

Это иллюстрация группировки терминов, а не проверенная поисковая стратегия. Третья группа сужает тему до выбранных компонентов. Перед применением нужно проверить терминологию, поддержку операторов и поля поиска на конкретной платформе. Составитель плагина не переводит выражение автоматически в синтаксис разных баз.

## Выполнение поиска

Назначение и итог выполнения учитываются раздельно:

| Назначение | Когда использовать |
| --- | --- |
| `pilot` — пробный | Проверка терминов, синтаксиса и масштаба выдачи |
| `main` — основной | Поиск, результаты которого планируется обработать в проекте |
| `update` — обновление | Повторный поиск для пополнения или актуализации материалов |

| Статус | Смысл |
| --- | --- |
| `completed` — завершён | Запланированная работа в рамках этого выполнения закончена |
| `partial` — частично | Работа остановлена до запланированного завершения |
| `failed` — ошибка | Выполнить поиск не удалось; подробности можно записать в примечании |

«Завершён» не означает, что найдены все релевантные публикации или завершён обзор.

### Даты и ссылки

Дата фактического поиска принимается в одном из форматов:

- `2026-11-11` — известен только календарный день.
- `2026-11-11T17:30:00+03:00` — известны дата и время со смещением.
- `2026-11-11T14:30:00Z` — дата и время в UTC.

Для даты со временем укажи также часовой пояс, например `Europe/Moscow` или `UTC`. Дата без времени сохраняется как дата, без добавления вымышленного часа. Дата внесения записи в журнал учитывается отдельно от даты поиска.

Дополнительно можно записать длительность в минутах, адрес результатов, путь к выгрузке, ссылку на Zotero и примечания. Ссылка Zotero может быть веб-адресом или URI вида `zotero://…`; она служит переходом к материалам, а не синхронизацией библиотек. Поле пути к выгрузке хранит указатель на файл, не импортируя его содержимое.

## Как понимать статистику

| Показатель | Что вводить |
| --- | --- |
| Показано результатов | Число, которое отобразила платформа; приблизительную оценку нужно отметить |
| Просмотрено записей | Сколько названий и/или аннотаций фактически просмотрено в этом выполнении |
| Отобрано после просмотра | Сколько просмотренных записей оставлено для следующего этапа работы |
| Выгружено записей | Сколько библиографических записей фактически экспортировано |

**Пусто означает «неизвестно», `0` означает известный нулевой результат.** Отобранных после просмотра не может быть больше просмотренных в рамках того же выполнения. Выгруженных может быть больше просмотренных: например, сначала экспортирована вся выдача, а просмотр начат позднее.

Сводные суммы относятся к выполнениям и могут содержать повторные записи и пересечения между запросами. Для суммы учитывается, в скольких выполнениях значение заполнено. Незаполненные значения не превращаются в нули.

Пробные, основные и обновляющие выполнения остаются различимыми в журнале и экспорте. Общая сумма журнала не является числом уникальных публикаций, числом включённых исследований или показателем полноты поиска. Способ удаления дубликатов и подтверждённые итоги можно описать в поле проекта «Работа с дубликатами».

## Материалы для исследований и рабочих задач

Открой вкладку **«Материалы»**, нажми **«Добавить материал»** и укажи название. Остальные поля необязательны. Поддерживаются статья, документация, отчёт, веб-страница, книга, видео и другой материал.

В карточке можно указать авторов или организацию, год, DOI, HTTP(S)-ссылку, пути к файлу и заметке внутри хранилища. Для документа без DOI оставь поле пустым. Пустой год сохраняется как неизвестный, без подстановки нуля.

Состояние просмотра и решение об отборе задаются отдельно. Для решения **«Исключён»** требуется причина. При редактировании сохраняется прошлое состояние. Один материал можно связать с несколькими запросами и выполнениями или оставить без привязки. Для поиска карточек доступны текст и фильтры типа, состояния просмотра, решения и выполнения.

Карточки добавляются вручную и не пересчитывают счётчики журнала. Автоматического объединения дублей, импорта RIS/BibTeX и аннотирования PDF пока нет. JSON переносит журнал вместе с материалами и историей; **«CSV — материалы»** выгружает отдельную таблицу. Сами PDF и заметки JSON не упаковывает, их пути остаются ссылками.

Каталог сохраняется в отдельных управляемых блоках того же Markdown-файла. Схема журнала v1 остаётся прежней. Без каталога JSON сохраняет прежний объект проекта v1. С каталогом используется контейнер `format: "searchtrail-project"`, `transferVersion: 1`, `project` и `catalog`; импорт поддерживает оба варианта.

## Версии и исправления

Снимок выполнения содержит название запроса на момент регистрации, идентификатор и номер версии, полное определение запроса. Последующие изменения стратегии сохраняют этот снимок.

Если ошибочно введены дата, статистика или примечание, запись можно исправить с указанием причины. Предыдущее состояние сохраняется в истории. Изменение самого поискового выражения оформляется новой версией запроса и новым выполнением.

## Хранение и экспорт

По умолчанию проекты хранятся в папке **Search Strategies** внутри хранилища; папку можно задать в настройках плагина. На каждый проект создаётся один Markdown-файл.

В файле есть два управляемых плагином блока: полные данные проекта в JSON и человекочитаемый отчёт. Текст пользователя вне этих блоков сохраняется при обновлении. Собственные замечания удобно дописывать вне управляемых блоков; содержимое сформированного отчёта обновляется из данных проекта.

Если другой редактор или экземпляр плагина успел изменить редакцию проекта, сохранение обнаруживает конфликт. Перечитай проект перед повторным внесением изменений. Повреждённые данные и неподдерживаемые версии формата не преобразуются молча.

| Экспорт | Назначение |
| --- | --- |
| Markdown | Читаемый отчёт для обсуждения, приложения к материалам или дальнейшего редактирования |
| CSV | Табличный журнал выполнений для обработки в редакторе таблиц |
| JSON | Полная структура проекта, включая версии запросов и историю исправлений |

Экспорт CSV предназначен для анализа журнала. Полная история проекта хранится в JSON; CSV не заменяет её.

### Перенос проекта через JSON

В панели нажми **«Новый проект»** и выбери **«Импортировать из JSON»**. На пустой панели такое же меню доступно через **«Создать первый проект»**. Выбери файл полного JSON-экспорта SearchTrail или вставь его текст. После успешного импорта проект будет выбран в панели автоматически. Пункт **«Создать пустой проект»** открывает обычную форму нового проекта.

Та же форма доступна через команду **«Импортировать проект из JSON»**. Плагин проверит формат данных и создаст отдельный Markdown-файл в настроенной папке, сохранив идентификаторы, версии запросов и историю исправлений.

Если в этой папке уже есть проект с таким идентификатором, импорт завершится отказом и существующий файл останется без изменений. Импорт служит переносу проекта; объединение двух расходящихся историй в этой версии не реализовано.

## Работа через MCP

Если в Obsidian включён **Local REST API with MCP** с extension API версии 3 или новее, SearchTrail автоматически добавляет 14 инструментов `searchtrail_*` в его MCP-сервер. Отдельный сервер и ключ для SearchTrail не требуются. Без Local REST API плагин продолжает работать через обычную панель.

Через MCP можно читать и создавать проекты, изменять поля проектов и запросы, записывать и исправлять выполнения, получать сводку, импортировать JSON и создавать экспорты. Изменения проходят проверки модели и хранения SearchTrail. История исправлений, снимки версий и заметки вне управляемых блоков сохраняются.

После установки сборки выключи и снова включи SearchTrail. В настройках SearchTrail появится строка о состоянии MCP. Если клиент не показывает новые инструменты, обнови его MCP-подключение. Инструменты `searchtrail_list_projects` и `searchtrail_get_project` читают проекты. Для изменений передаются прочитанные `revision` и `fingerprint`, а для материалов дополнительно `catalogFingerprint`.

MCP выполняет операции с данными внутри Obsidian. Проверка внешнего вида и заполнения форм остаётся отдельной задачей.

## Границы версии

В MVP нет автоматического выполнения запросов, получения статистики с сайтов, синхронизации с API Zotero или автоматического удаления дубликатов. Статистика относится к журналу; окончательный отбор публикаций выполняется исследователем.

Модель учитывает отдельные рекомендации [PRISMA-S](https://doi.org/10.1186/s13643-020-01542-z): различение источника и платформы, сохранение запроса, ограничений, дат и чисел по источникам. Плагин не проверяет соответствие всего обзора PRISMA и не подтверждает качество поисковой стратегии. Для различения записей, публикаций и исследований полезны [разъяснения PRISMA 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC8005925/) и [FAQ по учёту результатов](https://doi.org/10.5195/jmla.2022.1449).

## Разработка

Открой корень репозитория в VS Code. Требуемая версия Node.js указана в `package.json`; `.nvmrc` выбирает ветку 24.

| Команда | Результат |
| --- | --- |
| `npm run build` | Проверка типов и сборка |
| `npm run dev` | Пересборка при изменении исходников |
| `npm test` | Модель, хранение, экспорт и репозиторий |
| `npm run test:ui` | Поведение интерфейса в JSDOM |
| `npm run test:install` | Проверки установщика |
| `npm run check` | Сборка и все автоматические проверки |
| `npm run install:dev -- --vault "/absolute/path/Test Vault"` | Сборка и установка в явно указанное тестовое хранилище |
| `npm run package` | Сборка установочного ZIP-архива |

Перед установкой открой тестовое хранилище в Obsidian хотя бы один раз, чтобы появился каталог конфигурации. Для нестандартного каталога добавь `--config-dir .obsidian-dev`. Установщик обновляет только `main.js`, `manifest.json` и `styles.css`, сохраняя проекты и настройки. Он не включает плагин автоматически. После установки выключи и снова включи SearchTrail.

`npm run dev` не копирует файлы в хранилище и не перезагружает Obsidian. Задачи VS Code доступны через **Tasks: Run Task**; задача установки запрашивает путь к хранилищу.

Из каталога исходного кода выполни:

```bash
npm ci
npm run check
```

Для загрузки в Obsidian нужны собранный `main.js`, `manifest.json` и `styles.css`. Основа процесса разработки описана в [официальном образце TypeScript-плагина](https://github.com/obsidianmd/obsidian-sample-plugin).

Данные проверяются перед чтением и сохранением. Неизвестные числовые значения сохраняются как `null`; CSV-экспорт экранирует содержимое ячеек, которое могло бы интерпретироваться как формула. При сохранении используется `Vault.process`: проверяются номер редакции и соответствие текущих данных прочитанному состоянию. Пользовательский текст вне управляемых блоков сохраняется.

Автоматические проверки не подтверждают внешний вид, работу в конкретной версии Obsidian или мобильную совместимость. Эти сценарии проверяются отдельно в тестовом хранилище.

`npm run test:ui` проверяет формы и панель в JSDOM с подменой Obsidian API. `npm run test:install` проверяет установщик на временных хранилищах. Для упаковки исходников и готового плагина выполни `npm run package`; для этой команды нужен Python 3.

В CSV к потенциально исполняемым значениям добавляется защитный апостроф. Для точного переноса исходного текста запроса используйте кнопку копирования в плагине или полный JSON-экспорт.
